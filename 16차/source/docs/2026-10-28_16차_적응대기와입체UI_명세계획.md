현재 글자의 실제 최종 확인 ScanFrame으로 바로 다음 글자의 사전 부재가 확정되면, 명시적 adaptiveWait에서 해당 after를 다음 글자 동작의 선행 조건 대기로 이전한다.

다음 조건이 새로 보이면 조기 진행하고, 안 보이면 after가 끝난 후 기존 timeout이 시작된다.

기존 waitText 와터치전새 프레임 재확인/단일 Task를 유지한다.

사전 조건이 이미 있거나 확신할 수 없으면 원래 after 유지.

같은 글자는 원래 after와 부재 →재등장가드를 사용한다. pause/stop/대상 변경 시 선행 상태 폐기와 취소를 검증한다.

## 제어 재현과 최소 수리 범위 보완

실제 검사에서 최종 대상 확인 이후 제스처를 보류하고 Settings 활성화를 확정한 뒤 해제하자 이전 좌표 제스처가 완료됐다.

화면 전환 확인 전에 snapshot을 반환한 원래 Safety 실패는 이와 구분하며, 이번 제어 RED를 제품 수리의 근거로 사용한다. prepare 및 잠깐의 제어 창 대기 뒤 worker에서 대상을 다시 확인하고, 창 이벤트·일시 정지 세대의 허가를 main 전달 직전에 비 차단으로 재검사한다. main에서 창 조회를 기다리지 않는다.

Android에는 앱 전환과 제스처 전달을 원자적으로 묶는 API가 없으므로 모든 물리적 경합 제거를 보증하지 않는다.

worker 초기화 전 실행 →일시 정지 순서를 제어한 검사에서 paused =true인데 pauseStartedAt이 0으로 덮이고 300ms 동안 활성 시간이 303ms 증가했다.

초기화·시작·정지·일시 정지는 같은 모니터로 보호하고 현재 세대에서만 초기화하며 일시 정지 시작 시각을 보존한다.

이전 실행의 deadline을 새 실행 초기화 검증에 사용하지 않는다.

즉시 정지한 큐 작업의 측정 재초기화 금지도 별도 검사한다.

기존 UI 실 측 비교를 정지 후로 옮기거나 숫자 오차를 허용해 결함을 숨기지 않는다.

제품의 OCR 생략·축소·이미지 캐시는 추가하지 않는다.

별도 소유 기기 540×1140/210dpi 환경에서 15차와 16차를 동일 fixture·폰트배율·CPU/RAM·모델 시작 조건으로 재비교할 수 있다.

## 실제 저해상도 실패와 CPU 조건의 별도 비교

540×1140/210dpi·CPU2·RAM2048·swiftshader에서 실제 InputImage540×1140 과 글자 최소 ink26×28을 확인했다. 15차는 210068ms에 11회/23 터치,16차는 125091ms에 7회/15 터치로 각각 기한 실패했다.
