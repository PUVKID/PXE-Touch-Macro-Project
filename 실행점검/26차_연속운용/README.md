# PXE 26차 추가 연속 운용 검증

**같은 최종 APK를 대상으로 짧은 연속 운용을 추가 검사했습니다.** 제품 코드는 바꾸지 않았고, 검사 APK에만 아래 하네스를 추가했습니다. 기존 단위 106개·기기 89개 근거에 새로운 기기 검사 2개를 보탰습니다. 이 결과는 실제 게임이나 수년 연속 운용의 무오류 보장이 아닙니다.

| 조건 | 실제 실행 | 확인 범위 |
| --- | --- | --- |
| 환경 | 별도 Android 12/API 31 x86_64 검사 장치 | 사용자 블루스택·게임은 사용하지 않음 |
| 제품 | 버전 26 / 2.6.0, 최종 서명 APK | SHA-256 `c1df900cfd54489e96d77eca7453f3a72799c70af315c4080fbdd878a0be36e1` |
| 첫 검사 | OCR 터치 15회씩 5구간, 총 75회 | JUnit 1개 통과, 58.0초 |
| 두 번째 검사 | 목록 OCR 진입 → 상세 OCR 15회 → 뒤로가기 → 새로고침·재탐지, 5바퀴 | JUnit 1개 통과, 70.6초 |
| 연결 연속성 | 각 검사 안에서 같은 서비스와 같은 프로세스 유지 | 두 검사 사이의 별도 초기화는 수명 연속으로 합산하지 않음 |
| 종료 | 첫 검사는 없는 글자 대기에서 실제 정지 버튼, 두 번째는 정지 뒤 재진입 없음 | 정지 뒤 관측 구간의 추가 터치 없음 |

시간 표시는 소수 첫째 자리 반올림입니다. PSS는 각 구간 끝의 관측값이며 짧은 표본만으로 장기 메모리 누수가 없다고 증명하지 않습니다. 검사 화면에는 버튼 한 개만 있으며 사용자의 실제 전체 매크로 15회 시간으로 환산하지 않습니다.

매 구간 종료 때 캡처 대기 수 0·OCR 대기 해제·실행 기록 150줄 이하·실제 터치 수 일치를 확인했습니다. 이후 화면을 `어도비`로 바꾸고 `Adobe` 탐지를 계속해 추가 터치가 없는지, 실제 정지 버튼이 응답하는지 확인했습니다. 정지 뒤에도 대기하여 추가 터치가 없음을 확인했습니다. 이 새 검사에서 OCR 콜백을 의도적으로 보류한 것은 아니며, 제어된 지연 결과의 폐기 검사는 기존 근거를 재사용합니다. 중단의 검사 기준은 1.2초 안의 응답이며 진단 로그의 3ms를 정밀 입력 지연 측정으로 해석하지 않습니다.

## 16차와 후속 계열의 차이

| 구분 | 확인된 코드 | 해석 |
| --- | --- | --- |
| ‘대상 앱을 한 번 터치하세요’ | 16차·24차·26차 모두 활성 창 패키지가 비었을 때 같은 안내 | 후속 차수에 처음 추가된 안내가 아님 |
| 창 패키지 판별 | `WindowPackages`는 세 차수 바이트 동일 | 이벤트 누락·활성 창 불명확 상태를 모두 확정 대상 없이 처리 |
| 16차 | 창 조회 1.5초 제한과 대상·세대 확인 | 잘 실행됐다는 경험을 어떤 환경에서도 정지하지 않는다는 근거로 확대하지 않음 |
| 24차 계열 | 창 관측 순서·창 키 변경 시 허가 폐기·조회 지연 복구·복구 세대 검사 추가 | 창 전환이나 관측 경쟁에서 대기가 반복될 가능성은 있으나 과거 실제 오류 원인으로 확정하지 않음 |
| 26차 | 16차 기반, 늦은 창 조회는 중복 없이 기다림 | 유한 글자 대기의 조회 제한과 실제 오류·정지 처리는 유지 |
| 차수 이름 | 별도 25차 빌드 준비는 취소·24차로 병합된 기록 | 사용자가 지칭한 설치본이 어느 APK인지는 미확인 |

**AI 때문에 멈췄다고 단정할 근거는 없습니다.** 이번 두 검사는 같은 검사 앱 안의 목록·대화상자 전환이며 서로 다른 실제 앱·블루스택 6개 동시 실행·장시간 부하를 검증하지 않았습니다.

## 재현과 실패 보존

[추가 검사 소스](Sustained26Test.java)는 공개 26차의 `GuidedFlowTest`와 제품 클래스를 사용합니다. 별도 검사 장치에 최종 APK와 이 소스를 포함한 release AndroidTest APK를 설치하고 AndroidJUnitRunner에서 두 메서드를 선택 실행합니다. 실제 사용 중인 장치에서 실행하면 테스트 초기화가 접근성 설정과 검사 앱 화면을 바꾸므로 검사 전용 장치만 사용해야 합니다.

기존 검사 장치의 저장 공간 부족, 새 장치 연결 대기 실패, 빌드 성공 뒤 콘솔 원문 디코딩 실패를 원래 기록에 보존했습니다. 기동 실패를 제품 검사 성공으로 바꾸지 않았습니다. 검사 장치를 분리 준비한 뒤 최종 성공 실행을 별도로 기록했고, 빌드 원문은 보존하면서 혼합 인코딩의 표시 처리만 바꿨습니다. 제품 APK의 지문은 변하지 않았습니다.
