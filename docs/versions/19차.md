### LEVEL 1 · 앱 창을 확인하지 못할 때 기다리는 이유


19차는 화면을 눌러도 되는 앱인지 확인하는 요청이 취소됐을 때, 사용자가 정지한 경우와 구분해 복구하는 변경입니다.

Android 접근성 기능으로 입력을 전달하고 Java로 구현했으며 ML Kit의 한국어 OCR로 사진 속 글자를 읽습니다.

화면 확인 실패와 글자 없음은 다릅니다.

 확인을 못 했는데 글자가 없다고 판단하면 잘못된 뒤로가기나 스크롤이 실행될 수 있기 때문입니다.

복구 중에는 오래된 좌표를 누르지 않고 뒤로가기·스크롤·중복 차단 해제를 임의로 하지 않습니다. 새로 확인한 실제 대상 앱을 기준으로 이어 갑니다. 사용자의 정지, 서비스 연결 해제, 권한 오류와 전체 실행 시간 제한은 계속 적용합니다. 모든 오류를 무한히 재시도하는 기능이 아닙니다.

15회 중 7회를 마치고 8회째에서 화면 응답을 기다리는 예를 생각해 보십시오. 하단 창은 **7회 완료와 8회째 대기**를 따로 보여 주며 복구됐다고 앞 7회를 다시 실행하지 않습니다. 작은 접이식 창, 시간·상세 기록, 글자 인식·우선순위·반복·녹화·중복 방지는 그대로 유지합니다.

### LEVEL 1 · 설정에서 실제 입력까지


매크로에는 동작, 찾을 글자, 좌표, 검색 영역, 반복 횟수가 들어갑니다.

편집하고 저장한 다음 대상 앱과 글자를 확인하고 Android 접근성 제스처로 터치합니다.

그 결과는 실제 터치, 화면 위 제어 상태, 저장 JSON, 동작·인식·오류 기록으로 나뉩니다.

JSON은 이름과 값을 일정한 형식으로 저장한 파일입니다.

저장이 잘 됐다는 사실만으로 실제 화면을 읽을 수 있는 것은 아닙니다.

준비할 때는 매크로의 동작·반복·대기를 확인하고 글자마다 인식 방식과 검색 영역을 정합니다.

대상 앱과 접근성 서비스가 연결됐는지 확인한 뒤 실행하고, 화면 위 제어창의 정지·일시정지와 진행 기록을 살펴봅니다.

서비스가 연결되지 않으면 접근성 권한부터, 글자를 못 찾으면 인식 방식·영역·실제 접근성 글자·캡처 제한부터 확인합니다.

좌표나 반복이 맞지 않으면 화면 방향과 비율 좌표, 개별 동작·전체 매크로·목록 반복을 나눠 봅니다.

### LEVEL 1 · 소스와 검사 파일을 찾는 법


[source/](../../19차/source)는 앱을 만드는 소스 폴더입니다. [APK 파일정보](../../19차/APK_파일정보.json)는 설치 파일 식별 정보, [README](../../19차/README.md)와 [설치와 변경사항](../../19차/설치와_변경사항.md)은 사용·설치 안내입니다. [검증 결과](../../19차/검증_결과.md), [검증 요약](../../19차/검증_요약.json), [공개용 변경기록](../../19차/공개용_변경기록.md)은 당시 확인 범위와 변경을 보여 줍니다.

`MainActivity.java`는 앱 화면, `MacroService.java`는 실행 서비스에 해당합니다.

검사 도구 이름도 역할이 다릅니다. `check_artifacts.py`는 APK·이전 차수 보존·이름·버전·서명을, `check_device.py`는 지정한 PXE19 시험 기기에서 회귀를 확인합니다. `check_regression.py`는 실제 javac/JUnit으로 순수 모델 검사를, `check_utf8.py`는 생성물·라우팅 상태를 제외한 텍스트 인코딩을 검사합니다. `check_performance.py`는 같은 OCR 시험 자료에서 이전/적응 실행 시간을 측정하는 도구이지 그 파일 존재가 새 성능 측정을 뜻하지는 않습니다.

직접 빌드하려면 해당 차수의 완전한 Gradle 프로젝트와 manifest·리소스·SDK·JDK·서명 입력이 필요합니다.

SDK는 Android 개발 도구, JDK는 Java 개발 도구입니다.

정확한 명령은 [소스 README](../../19차/source/README.md)와 build.gradle을 확인합니다.

실제 접근성 권한은 사용자가 허용해야하며 공개 소스만으로 기존 서명 앱을 업데이트할 수 있는 것은 아닙니다.

일부 소스나 설정 예제만으로 완성 APK가 되지도 않습니다.

### LEVEL 1 · 창 전환을 늦게 알게 된 실패


시험 중 실제 활성 앱 창은 바뀌었는데 서비스가 기억한 창 변경 번호는 아직 같은 순간이 발견됐습니다.

이 번호는 예전 화면에서 받은 입력 허가가 아직 유효한지 확인하는 데 쓰입니다.

별도 진단에서 새 창 정보를 확인한 시점과 이벤트 처리 사이 약 57밀리 초가 관측됐습니다.

기존 차수에도 같은 보호 코드가 있었으므로 새 취소 복구만의 잘못이라고 확정하지 않습니다.

뒤의 진단이 통과해도 첫 실패는 남습니다.

보강 후에는 수락한 활성·초점 창의 식별이 달라지면 예전 입력 허가를 버립니다.

취소되거나 기한이 지난 응답은 새 관측으로 쓰지 않으며 앱 화면을 담당하는 메인 스레드에 동기 창 조회를 추가하지 않습니다.

검사에서는 `activePackage()`로 새 창을 확인한 뒤 허가가 폐기되는지 봤습니다.

마지막 확인 뒤 창이 바뀌고 추가 조회·이벤트가 아직 하나도 오지 않은 모든 순간까지 막았다는 보장은 아닙니다.

### LEVEL 1 · 남아 있는 적응 대기와 입체 표시


**다음 글자에 맞춰 진행**은 기본 꺼짐입니다.

켜도 모든 대기를 없애지 않습니다.

같은 인식 방식·영역의 연속 글자 동작에서 다음 글자가 미리 없다는 것을 확인한 경우, 완료 후 기다릴 시간을 다음 글자 기다림에 사용하고 새 글자가 보이면 진행합니다.

이미 보이는 조건·수동 대기·반복 간격·무작위 대기는 유지합니다.

바로 다음 터치가 같은 위치면 사라졌다가 다시 나타나는 것을 확인하지만 모든 개별·전체 반복의 중복을 막는 기능은 아닙니다.

목록의 사라짐 확인은 별도 설정이며 기존 수치를 일괄 줄이거나 터치 전 재확인을 끄지 않습니다.

단계 시간 안에는 OCR·캡처·대기 같은 작은 작업이 들어갑니다.

따라서 이 시간들을 모두 더하면 같은 시간을 두 번 셀 수 있습니다.

전체 반복의 외부 시간과 내부 집계도 구분합니다.

실행 준비 전에 정지·일시 정지했으면 예전 대기 열이 측정을 다시 초기화하지 못하도록 실행 번호를 확인합니다.

개별 글자 터치는 제어 창 준비 뒤 대상을 확인하고 실제 전달 직전에 창 변경·일시 정지 번호를 다시 봅니다.

이 추가 검사는 개별 TEXT_TAP에 적용되며 목록 진입의 대상 확인·중복 예약 순서는 유지합니다.

홈의 입체 PXE 모델은 OBJ 파일의 224 정점·168 면을 실제 투영하고 깊이·조명을 계산해 그립니다.

정점은 입체 도형의 점, 면은 점들을 이은 표면입니다.

상태가 바뀔 때 그리며 상 시 애니메이션은 없습니다.

나눔고딕 Bold·라이트/다크·제어 흐름은 유지합니다. 15회 120초는 통제 시험 목표이며 실제 게임이나 사용자 블루스택의 99% 성공·무오류 실적이 아닙니다.

### LEVEL 1 · 저장값에 허용되는 범위


`Macro`의 schema1은 저장 형식의 첫 규칙입니다.

이름·시작 번호·전체 반복·간격·시작 지연·최대 시간·동작 목록을 저장합니다.

동작은 1~500개이고 시작 번호는 실제 목록 안에 있어야합니다.

전체 반복 0~100,000, 간격·시작 지연 0~600,000ms, 최대 시간 0~1,440분 범위를 검사합니다.

숫자 0의 의미는 항목마다 다를 수 있으므로 임의 해석하지 않습니다.

각 `Step`은 동작 종류·좌표·검색 영역·글자 비교·인식 출처·실패 정책·반복·대기·분기 번호입니다.

비율 좌표와 유한한 숫자, 영역의 좌우·상하 순서, 문구 존재, 정규식 문법, 앱 패키지명, 이동·분기 번호를 검사합니다.

정규식은 글자 패턴을 표현하는 문법이며 패키지명은 앱 식별자입니다.

저장값 통과와 기기에서 읽고 누를 수 있음은 별도 조건입니다.

### LEVEL 1 · 실제 검사 결과와 비교


별도 검증자가 최종 소스·납품 APK에서 기존 114개 +새 6개 =120개 기기 검사를 통과했습니다. 단위 109개·20 클래스는 실패·오류·생략 0, 린트 0건입니다. 각 묶음은 아래와 같으며 소요 시간과 제한 시간은 다릅니다.

| required-check-plan.json |52 |320.390초 |720초 |
| recognition-check-plan.json |12 |34.141초 |240초 |
| adaptive-check-plan.json |25 |90.562초 |480초 |

장기 지연·조회 취소·하단 복구 표시·15회 중간 진행 보존·다른 앱 무터치·권한 오류·전체 기한을 구분해 검사했습니다.

이는 시험 환경의 결과이며 사용자별 장시간 운용 보증이 아닙니다.

완료 수와 현재 회차, 글자 없음과 읽기 실패, 정지와 복구 대기를 따로 읽고 화면 글자가 들어갈 수 있는 운영 로그는 공유 전에 확인합니다.

[18→19 전체 비교](../revision-audit/19차.md)는 추가·수정·삭제뿐 아니라 주석·공백·개행과 바이너리 크기·해시를 확인하는 자료입니다.

### LEVEL 2 · 조회 취소가 실행 정지와 다른 이유


19차에서 복구하는 것은 **대상 앱 창을 확인하는 개별 조회의 취소**입니다.

사용자가 매크로를 정지했거나 서비스 연결이 끊어진 상태와 같은 뜻이 아닙니다.

실행이 유효한 동안 조회를 새로 확인하되 복구 중 오래된 좌표, 뒤로가기, 스크롤, 중복 잠금 해제를 쓰지 않습니다.

정상 화면에 글자가 없는 조건과 화면을 읽지 못한 조건을 분리해야 잘못된 실패 행동을 막을 수 있습니다.

권한 오류·사용자 정지·서비스 해제·전체 최대 시간은 계속 적용합니다.

이 흐름은 편집·저장된 동작/글자/좌표/영역/반복을 입력으로 받아 대상 앱과 글자를 확인하고 접근성 제스처를 전달한 뒤 진행 상태를 갱신합니다.

출력은 실제 입력, 플로 팅 상태, 매크로 JSON, 동작·인식·오류 기록입니다.

Android 접근성·Java·ML Kit 한국어 OCR이 각각 입력 전달·구현·글자 인식을 맡습니다.

저장 설정과 현재 관측을 결합해야 입력이 가능하며 저장 성공만으로 대상 확인을 생략할 수 없습니다.

하단 진행 창도 같은 상태 구분을 보여 줍니다. 15회 중 7 완료/8회째 복구 대기라면 완료 수 7을 보존한 채 원래 위치에서 이어 갑니다. 복구를 전체 반복의 새 시작으로 처리하면 이미 끝난 7회를 다시 수행하게 됩니다.

### LEVEL 2 · 새 관측과 입력 허가의 관계


첫 경계 실패에서는 실제 활성 창이 바뀌었지만 이벤트 세대가 그대로였습니다. 별도 진단이 본 약 57ms는 새 창 메타 확인과 서비스 이벤트 처리 사이의 간격입니다. 이전 차수와 같은 코드가 있던 부분이므로 취소 복구가 새로 만든 회귀라고 확정하지 않습니다. 진단 통과와 최초 실패는 모두 남깁니다.

수락한 활성·초점 창의 식별 변화에 입력 허가 폐기를 연결하면, 오래된 화면의 허가가 새 관측 뒤까지 남지 않습니다.

취소·기한 경과 결과는 관측을 갱신하지 않으며 메인 스레드에서 동기 조회를 기다리지 않습니다. `activePackage()`로 새 창을 확인하는 검사는 이 **수락된 관측→허가 폐기** 연결을 확인합니다.

관측·이벤트가 아직 모두 오지 않은 전환 순간까지 원자적으로 막았다는 의미는 아닙니다.

### LEVEL 2 · 대기·시간 측정·표시의 서로 다른 책임


‘다음 글자에 맞춰 진행’은 기본 꺼짐입니다.

같은 인식 방식·영역의 연속 글자 조건에서 다음 글자가 사전에 없을 때만 완료 후 대기를 다음 조건 기다림으로 바꿉니다.

다음 글자가 나타나면 진행하지만 이미 보이던 조건·수동 WAIT·반복 간격·무작위 대기는 유지합니다.

다음 글자 터치가 같은 위치라면 사라짐과 재등장을 확인합니다.

이것은 모든 명시 반복을 차단하는 장치가 아니며 목록 사라짐 설정도 별도입니다.

기존 프로필 수치나 터치 전 재확인을 일괄 바꾸지 않습니다.

시간의 관계도 중첩됩니다.

단계 시간에는 OCR·캡처·설정 대기 일부가 들어가므로 네 값을 단순 합산하면 중복 계산이 됩니다.

외부 전체 반복 측정과 내부 집계를 구분합니다.

실행 준비 전에 일시 정지/정지한 경우 이전 큐가 측정을 재초기화하지 않게 세대를 확인합니다.

개별 TEXT_TAP은 제어 창 준비 뒤 대상 확인과 실제 전달 직전 창·일시 정지 세대를 대조하지만, 목록 진입은 기존 대상 확인·중복 예약 순서를 유지합니다.

화면의 OBJ 모델은 224 정점·168 면을 원근 투영·깊이 정렬·조명으로 그린 결과입니다. 상태 변경이 갱신을 일으키며 상 시 애니메이션/예약 렌더 루프는 없습니다. 나눔고딕 Bold와 라이트/다크·제어 흐름을 유지합니다. 입체 표시나 15회 120초 목표를 실제 게임 99% 성공 근거로 연결할 수는 없습니다.

### LEVEL 2 · 설정 계약이 실행까지 보장하지 않는 이유


Macro의 schema1 JSON은 이름·시작 번호·전체 반복·간격·시작 지연·최대 시간·동작 배열을 저장합니다. 1~500 동작과 배열 안 시작 번호, 활성 Step 검증을 요구합니다.

전체 반복 0~100,000, 간격/시작 지연 0~600,000ms, 최대 시간 0~1,440분입니다.

Step은 종류·좌표·영역·글자 비교·인식 출처·실패 정책·반복·대기·분기 번호를 가집니다.

유한 비율 좌표, 영역 순서, 문구, 정규식, 앱 패키지, 이동·분기 번호의 유효성을 검사합니다.

이 계약은 잘못된 저장 입력을 거르지만 접근성 연결이나 실제 OCR 가용성을 만들지는 않습니다.

따라서 사용 흐름은 매크로/동작·반복·대기 선택→글자 방식·영역 설정→대상 앱·서비스 확인→실행과 정지/일시정지 관측입니다.

서비스 실패는 권한·연결, 탐지 실패는 방식·영역·접근성 텍스트·캡처 제한, 좌표/반복 불일치는 방향·비율·개별/전체/목록 반복에 연결해 확인합니다.

운영 기록에는 인식 글자가 들어갈 수 있어 공개 전에 확인합니다.

### LEVEL 2 · 자료와 검사 도구의 역할 연결


[source](../../19차/source) 안의 MainActivity는 화면, MacroService는 실행 서비스입니다. [소스 README](../../19차/source/README.md)와 build.gradle에서 같은 차수의 Gradle·SDK·JDK·서명 조건을 확인합니다.

완전한 manifest·리 소스가 필요하며 일부 소스나 설정만으로 단독 APK가 되지 않습니다.

접근성은 사용자가 허용해야하고 공개 소스만으로 기존 서명 업데이트 권한을 얻지 않습니다.

[APK_파일정보.json](../../19차/APK_파일정보.json)은 파일 식별, [README](../../19차/README.md)·[설치와 변경사항](../../19차/설치와_변경사항.md)은 실행 준비, [검증 결과](../../19차/검증_결과.md)·[요약JSON](../../19차/검증_요약.json)은 관측, [공개 변경기록](../../19차/공개용_변경기록.md)은 차이를 연결합니다.

도구도 같은 분업을 따릅니다. check_regression은 javac/JUnit 순수 검사, check_utf8은 생성 물·라우팅상태 제외 엄격 디코딩, check_performance는 동일 OCR fixture의 이전/적응 측정입니다.

존재하는 도구 목록은 이 모든 시험을 지금 새로 실행했다는 기록이 아닙니다.

### LEVEL 3 · 설치와 실행 준비


19차/1.9.0은 대상 앱 창 조회 취소 뒤의 복구와 하단 대기 표시를 보강한 버전입니다.

소스 일부만으로 설치 APK 또는 기존 서명 앱의 업데이트를 보장하지 않습니다.

설치 뒤 접근성 서비스는 사용자가 직접 허용해야 합니다.

매크로의 동작·반복·대기를 확인하고 글자 조건의 인식 방식과 검색 영역을 지정합니다.

대상 앱과 서비스 연결을 확인한 다음 실행하십시오.

편집·저장된 글자·좌표·영역·반복 설정은 대상 확인과 제스처 전달을 거쳐 실제 터치, 플로팅 상태, 매크로 JSON, 동작·인식·오류 기록으로 이어집니다.

실행 중 정지·일시정지에 접근할 수 있는지 확인합니다.

작은 접이식 창, 시간·상세 기록, 우선순위·녹화·중복 방지 등 기존 기능은 유지합니다.

자료는 [APK 파일정보](../../19차/APK_파일정보.json), [README](../../19차/README.md), [설치와 변경사항](../../19차/설치와_변경사항.md), [검증 결과](../../19차/검증_결과.md), [검증 요약](../../19차/검증_요약.json), [공개 변경기록](../../19차/공개용_변경기록.md)으로 구분합니다.

APK 파일 식별, 설치 절차, 실제 검사 결과를 서로 대신하는 증거로 사용하지 않습니다.

### LEVEL 3 · 복구 중 확인할 화면과 중단 조건


**15회 중 7회 완료·8회째 대기** 상태에서 창 조회가 복구되면 완료 수는 7을 유지하고 원래 흐름을 이어야합니다.

앞선 7회를 다시 실행하거나 완료 수를 초기화하는 동작은 이 설명의 기대 동작이 아닙니다.

복구 중에는 오래된 좌표 터치·뒤로가기·스크롤·중복 차단 해제를 실행하지 않고 새 대상 앱 확인을 기다립니다.

개별 조회 취소와 사용자 정지·서비스 해제·권한 오류·전체 최대 실행 시간은 구별합니다.

모든 예외를 계속 재시도하는 기능으로 사용하지 마십시오.

서비스 연결 실패는 접근성 권한과 실제 연결부터 확인합니다.

글자 탐지 실패는 인식 방식·검색 영역·접근성 텍스트·캡처 제한을 확인하고, 좌표/반복 불일치는 화면 방향·비율 좌표·개별/전체/목록 반복을 따로 확인합니다.

기록에서는 글자 없음과 읽기 실패, 정지와 복구 대기, 현재 회차와 완료 수를 구분하십시오.

운영 로그에는 인식한 화면 문구가 포함될 수 있으므로 공유 전에 확인합니다.

### LEVEL 3 · 설정값과 적응 대기 점검


`Macro` schema1 JSON에는 이름·시작 번호·전체 반복·반복 간격·시작 지연·최대 시간·동작 배열이 들어갑니다.

동작 수 1~500개, 시작 번호의 배열 범위, 활성 `Step.validate`를 검사합니다.

전체 반복은 0~100,000, 간격·시작 지연은 0~600,000ms, 최대 시간은 0~1,440분입니다. `Step`의 종류·좌표·검색 영역·문구 비교·인식 출처·실패 정책·반복·대기·분기 번호를 확인하십시오.

유한 비율 좌표와 영역 순서, 문구 존재·정규식·패키지명·이동/분기 번호가 유효해도 실제 접근성/OCR 연결은 별도로 필요합니다.

‘다음 글자에 맞춰 진행’은 **기본 꺼짐**입니다.

켰을 때 같은 인식 방식과 영역의 연속 글자 동작에서 다음 글자의 사전 부재가 확인된 경우에만 완료 후 대기가 다음 조건 대기로 옮겨집니다.

이미 보이는 조건, 수동 대기, 반복 간격, 무작위 대기는 유지합니다.

바로 다음 터치가 같은 위치를 가리키면 사라짐·재등장을 확인합니다.

모든 명시 반복이나 전체 반복 경계를 막는 기능은 아니며 목록의 사라짐 확인은 별도 설정입니다.

기존 프로필 수치와 터치 전 재확인을 일괄 변경하지 않습니다.

측정 기록의 단계 시간에는 OCR·캡처·설정 대기가 포함되므로 네 값을 더해 전체 시간으로 읽지 마십시오.

전체 반복의 외부 측정과 내부 집계도 구분합니다.

준비 직후 정지·일시 정지한 실행의 대기 열이 측정을 초기화하지 않는지, 개별 TEXT_TAP이 제어 창 준비 뒤 대상 확인과 전달 직전 창·일시 정지 세대 확인을 거치는지 봅니다.

목록 진입은 기존 대상 확인·중복 예약 순서입니다.

홈의 OBJ는 224 정점·168 면을 투영·깊이 정렬·조명 계산하여 표시하며 상태 변경 시 갱신합니다. 상시 애니메이션·예약 렌더 루프는 없습니다. 나눔고딕 Bold·라이트/다크·기존 제어를 유지합니다. **15회 120초는 시험 목표**이며 실제 게임·사용자 블루스택의 99% 성공이나 무오류 측정이 아닙니다.

### LEVEL 3 · 검사 실행 위치와 관측 결과 읽기


화면 진입은 `MainActivity.java`, 실행은 `MacroService.java`에서 확인합니다. `check_regression.py`는 javac/JUnit 순수 모델, `check_utf8.py`는 생성물·라우팅 상태 제외 엄격 디코딩, `check_performance.py`는 동일 OCR fixture의 이전/적응 실행 측정용입니다.

도구의 존재를 새 실행 결과로 세지 않습니다.

### LEVEL 3 · 알려진 창 전환 경계와 전체 비교


전체 회귀의 최초 실패는 활성 창이 바뀌었지만 이벤트 세대가 아직 같았던 경계입니다.

별도 진단에서 새 창 메타 확인과 이벤트 처리 사이 약 57ms를 관측했습니다.

이전 차수와 같은 보호 코드였으므로 취소 복구 수정의 회귀로 확정하지 않습니다.

수락한 활성·초점 창 식 별이 달라지면 예전 허가를 폐기하고 취소·기한 지난 응답을 관측에 쓰지 않도록 보강했습니다.

메인 스레드에 동기 창 조회는 추가하지 않았습니다.

`activePackage()`로 새 창을 확인하는 검사 통과는 **관측된 변화 뒤 허가 폐기**의 근거입니다. 마지막 확인 뒤 추가 조회나 이벤트 없이 일어난 모든 전환까지 검증한 것은 아닙니다. 최초 실패도 보존합니다.

### LEVEL 4 · 조회 취소와 실행 수명의 분리


19차는 대상 창을 확인하는 비동기 조회가 취소되는 경우를 실행 전체의 취소와 분리합니다.

Android 접근성으로 입력을 전달하고 Java 실행 서비스와 ML Kit 한국어 OCR을 결합합니다.

동작·화면 문구·좌표·영역·반복 설정은 편집/저장 후 대상과 글자 확인, 제스처, 진행 갱신을 거쳐 터치·플로 팅 상태·JSON·동작/인식/오류 기록을 만듭니다. `MainActivity`와 `MacroService`의 화면/실행 책임은 유지합니다.

복구의 불변 조건은 **새 대상 확인 이전 입력 금지와 실행 수명 유지**입니다.

오래된 좌표, 뒤로가기, 스크롤, 중복 차단 해제를 복구 수단으로 사용하지 않습니다.

늦은 응답과 새 확인을 구별하며 정지·서비스 해제·전체 최대 시간·권한 오류는 계속 적용합니다.

예외 전체를 재시도 대상으로 확대하거나 종료 문구만 없애는 설계가 아닙니다.

진행 표시 또한 실행을 재시작하지 않습니다. 15회 중 7회 완료/8회째 대기라면 완료 수와 현재 동작을 유지해 복구 후 이어 갑니다.

기존 작은 접이식 창·시간·상세 실행 기록·인식·우선순위·반복·녹화·중복 방지를 보존합니다.

입력 설정을 고친 복구와 관측을 다시 얻는 복 구를 혼합하지 않는 것이 변경 범위의 핵심입니다.

### LEVEL 4 · 관측 세대와 전달 허가의 결합


회귀 실패는 실제 활성 창 변경이 이벤트 세대 변경보다 앞서는 경합을 보여 주었습니다. 별도 진단에서 새 창 메타 확인과 이벤트 처리 사이 약 57ms가 관측됐습니다. 같은 보호 코드가 이전 차수에도 있으므로 신규 취소 복구의 회귀라는 인과는 확정되지 않았고 최초 실패를 보존합니다.

수락한 활성·초점 창의 식별 변화가 이전 전달 허가를 무효화하게 보강합니다.

취소·기한 지난 결과는 관측 갱신에 사용하지 않고 메인 스레드에 동기 창 조회를 추가하지 않습니다. `activePackage()` 조회가 새 활성을 확정하면 그 수락된 관측도 세대를 갱신합니다.

따라서 해당 검사의 증명 범위는 관측→세대 갱신→옛 허가 폐기입니다.

추가 관측과 이벤트가 모두 없는 물리적 전환 틈의 원자 차단은 **보장하지 않습니다**.

### LEVEL 4 · 적응 실행과 측정의 경계


`adaptiveWait` 성격의 ‘다음 글자에 맞춰 진행’은 기본 꺼짐입니다.

같은 인식 방식/영역의 연속 글자 동작에서 다음 글자의 사전 부재가 확정될 때 완료 후 대기를 선행 조건 대기로 전환합니다.

이미 존재하는 다음 조건·수동 WAIT·반복 간격·무작위 대기를 유지하고 같은 위치의 다음 글자 터치는 부재→재등장을 요구합니다.

개별 명시 반복과 전체 반복 경계를 전부 차단하는 정책은 아니며 목록 사라짐 설정은 독립적입니다.

저장 프로필 수치와 전달 전 재확인을 일괄 약화하지 않습니다.

단계 측정과 OCR·캡처·설정 대기는 포함 관계이므로 합계로 전체 시간을 구성하면 중복입니다.

외부 반복 측정과 내부 집계를 구별합니다.

준비 전에 정지/일시 정지된 작업은 실행 세대로 걸러 측정 재초기화를 막습니다.

개별 TEXT_TAP은 제어 창 준비 뒤 대상 조회, 실제 전달 직전 창·일시 정지 세대 대조를 추가하지 만 목록 진입의 기존 대상 확인·중복 예약 순서는 유지합니다.

표시는 실행 엔진과 분리됩니다. 실제 OBJ 224 정점·168 면을 원근 투영하고 깊이 정렬·조명 계산하되 상태 변경에만 갱신합니다. 연속 렌더 루프 없이 나눔고딕 Bold·라이트/다크·제어 흐름을 유지합니다. 이 구조나 15회 120초 목표는 게임/사용자 블루스택 99% 성공과 무오류 성과가 아닙니다.

### LEVEL 4 · 저장 계약과 실행 가능성


`Macro` schema1은 이름·시작 번호·전체 반복·간격·시작 지연·최대 시간·동작 배열을 직렬화합니다.

동작 1~500개와 배열 안 시작 번호, 활성 Step 검증을 요구합니다.

반복 0~100,000, 간격/지연 0~600,000ms, 최대 시간 0~1,440분은 입력 범위입니다. `Step`은 종류·좌표·검색 영역·문구 비교·인식 출처·실패 정책·반복/대기·분기 번호를 보존하며 유한 비율 좌표·영역 순서·문구·정규식·패키지명·이동/분기 참조를 검증합니다.

JSON 계약 통과와 기기의 접근성/OCR 가용성은 다른 계층입니다.

운영 준비도 이 경계를 따릅니다.

매크로/동작/대기 검토→글자 방식/영역 지정→대상 앱/서비스 확인→실행 및 정지/일시정지 관측 순서입니다.

연결 실패는 권한/서비스, 인식 실패는 방식/영역/접근성 텍스트/캡처 제한, 좌표·반복 불일치는 방향/비율/개별·전체·목록 반복으로 나눠 진단합니다.

현재 회차·완료 수와 부재·읽기 실패, 정지·복구 대기를 합치지 않으며 운영 로그의 화면 문구는 공개 전에 검토합니다.

### LEVEL 4 · 소스·도구·재현 조건


[source](../../19차/source)의 MainActivity/MacroService와 [소스 README](../../19차/source/README.md)·build.gradle을 함께 읽습니다.

동일 차수의 Gradle 프로젝트에 manifest·리소스·SDK·JDK·서명 입력이 필요합니다.

일부 소스/설정 예제로 단독 APK를 보장하지 않고 공개 소스로 기존 서명 업데이트 권한을 얻는 것도 아닙니다.

실제 접근성 허용은 사용자 조작입니다.

[APK 정보](../../19차/APK_파일정보.json), [README](../../19차/README.md), [설치 안내](../../19차/설치와_변경사항.md), [검증 결과](../../19차/검증_결과.md), [요약 JSON](../../19차/검증_요약.json), [공개 변경기록](../../19차/공개용_변경기록.md)은 각각 파일/준비/관측/변경 근거입니다. check_artifacts는 APK·보존·식별/서명, check_device는 소유 PXE19회귀, check_recognition_device는 제한된 집중 검사, check_upgrade는 18 →19 데이터 보존을 담당합니다. check_performance는 동일 OCR fixture의 이전/적응 측정, check_regression은 실제 javac/JUnit 순수 모델, check_utf8은 생성 물·라우팅 상태를 제외한 엄격 디코딩입니다.

이 도구 목록만으로 새 실행을 주장하지 않습니다.

### LEVEL 4 · 바뀐 점·차이점

### 이 차수 원래 안내의 세부 조건


### 관측한 창 전환과 입력 허가


전체 회귀 검사에서 실제 활성 창이 바뀌었는데 창 변경 이벤트 세대는 아직 그대로인 경계 실패를 확인했습니다.

이전 차수와 같은 보호 코드였으며, 새 취소 복구 수정의 회귀라고 단정하지 않습니다.

별도 진단에서는 새 창 메타를 확인한 시점과 서비스 이벤트 처리 사이 약 57밀리 초의 공백을 관측했습니다.

진단의 통과로 최초 실패를 삭제하지 않습니다.

실제로 수락한 활성·초점 창 식별이 바뀌면 이전 전달 허가도 폐기하도록 보강합니다. 취소되거나 기한이 지난 결과는 관측 갱신에 사용하지 않습니다. 메인 스레드에 동기 창 조회를 추가하지 않습니다. 아직 관측하지 못한 모든 운영체제 전환까지 원자적으로 차단한다는 보장은 아닙니다.

기존 전달 경계 검사는 `activePackage()`로 새 창 활성을 확정하며, 이 조회도 수정 후에는 수락된 관측으로 세대를 갱신합니다.

따라서 해당 통과는 새 관측으로 이전 허가를 폐기하는 동작을 확인한 결과입니다.

마지막 조회 뒤 전환하고 추가 조회와 이벤트가 모두 도착하지 않은 모든 틈까지 검증한 결과로 확대하지 않습니다.

### 적응 실행과 실제 입체 모델


매크로 설정의 **다음 글자에 맞춰 진행**은 기본 꺼짐입니다.

켜면 같은 인식 방식과 영역의 연속 글자 동작에서 다음 글자의 사전 부재를 확인한 경우, 완료 후 대기를 다음 조건 대기로 바꿔 새 글자가 보이면 진행합니다.

이미 보이는 조건·수동 대기·반복 간격·무작위 대기는 유지합니다.

바로 다음 글자 터치가 같은 위치를 가리키면 사라짐과 재등장을 확인합니다.

개별 동작의 명시적 반복이나 전체 반복 경계를 모두 차단하는 기능은 아닙니다.

목록 탐지의 기존 사라짐 확인 설정은 별도로 유지합니다.

기존 프로필의 숫자를 일괄 축소하거나 터치 전 재확인을 끄지 않습니다.

실행 측정은 단계·OCR·캡처·설정 대기의 실제 시간을 구분합니다. 단계 시간에는 하위 작업이 포함되므로 네 값을 더한 숫자를 전체 시간으로 사용하지 않습니다. 전체 반복의 외부 측정과 내부 집계를 구분합니다.

실행 준비보다 먼저 일시정지하거나 정지해도 이전 대기열 작업이 측정값을 다시 초기화하지 않도록 실행 세대를 확인합니다.

개별 글자 터치는 제어창 준비 뒤에 대상을 확인하고, 실제 전달 직전에 관측된 창 변경과 일시정지 세대를 다시 대조합니다.

이 추가 전달 검사는 개별 `TEXT_TAP` 경로에 적용합니다.

목록 진입 터치는 기존의 대상 확인과 중복 예약 순서를 유지합니다.

홈의 PXE 모델은 실제 OBJ 224 정점·168 면을 읽어 원근 투영·깊이 정렬·조명으로 그립니다. 상태가 바뀔 때 갱신하며 상시 애니메이션·예약 렌더 루프는 없습니다. 나눔고딕 Bold와 기존 라이트/다크·제어 흐름을 유지합니다.

15회 120초는 통제 시험에서 측정할 목표입니다. 실제 게임·사용자 블루스택의 성공률 99% 또는 무오류를 코드만으로 보장하지 않습니다. 납품 검사 결과에 실제 실행 범위를 기록합니다.

### 매크로 저장과 실행 입력 검증


`Macro`는 schema1의 JSON으로 이름·시작 번호·전체 반복·반복 간격·시작 지연·최대 시간·동작 배열을 직렬화합니다. `validate`는 동작 1~500개, 시작 번호가 실제 배열 범위 안인지 검사하고 활성 동작에 `Step.validate`를 적용합니다.

전체 반복은 0~100,000, 간격·시작 지연은 0~600,000ms, 최대 시간은 0~1,440분 범위입니다.

`Step`은 동작 종류·좌표·검색 영역·글자 비교·인식 출처·실패 정책·반복과 대기·분기 번호를 저장합니다.

입력 검증은 화면 비율 좌표와 유한 값, 검색 영역의 좌우/상하 순서, 문구 존재, 정규식 문법, 앱 패키지 명과 이동/분기 번호를 함께 확인합니다.

저장 JSON의 schema 통과와 실제 장치의 접근성/OCR 가용성은 별도 조건입니다.
