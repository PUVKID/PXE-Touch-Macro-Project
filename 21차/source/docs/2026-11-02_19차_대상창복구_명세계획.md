# 19차 대상 창 지연·조회 취소 복구

확인일: 2026-11-02. 요구는 대상 앱 창 확인 응답 지연으로 탐지가 종료되지 않도록 해결하는 것입니다. 기존18차를 보존하고19차에만 변경합니다. 사용자 기기의 실제 설치 버전과 과거 오류 원문은 확보하지 않았습니다.

## 실제 조사 결과와 범위

16차는 창 조회의1.5초 지연을 외곽 실행 종료로 전달합니다. 17·18차와19차 초기 복사본은 `AwaitTimeout` 및 `QueryLane.Busy`의 원인 체인을 확인해 단일 조회를 유지하며 무터치 복구합니다. 같은 지연을 다시 주입해 성공한 것을 새로운 결함 RED나 사용자 실제 원인으로 표현하지 않습니다.

별도 `WindowSource` 조회가 `CancellationException`으로 끝나면 현재 `foregroundPackage`는 실제 실행 세대·연결 상태와 구분 없이 취소를 전달합니다. 새 제어 재현으로 실제 실행은 유효한 조회 취소와 사용자 정지·연결 해제를 구분할 수 있는지 확인한 뒤 최소 변경합니다. 메시지 문자열이나 모든 예외를 근거로 무한 재시도하지 않습니다.

복구 대기는 현재 실행 화면에서1순위 확인으로 남을 수 있습니다. 하단 상태에 실제 창 복구 대기와 정지 가능 상태를 표시하고, 복구 후에는 기존 현재 동작과 반복 완료 수를 유지합니다. 오류 기록에는 개인정보를 추가하지 않고 실제 빌드 버전과 오류 종류를 구분할 수 있게 합니다. 이미 존재하는 운영 기록은 삭제하지 않습니다.

## 성공 조건

- 창 지연은 단일 조회·중단 가능한 무터치 복구를 유지합니다. 지연 조회가 돌아오면 이전 좌표와 결과를 폐기하고 새 조회로 확인합니다.
- 실행 세대와 서비스 연결이 유효한 개별 창 조회 취소는 새 조회를 기다립니다. 실제 정지·연결 해제·전체 최대 실행 시간은 계속 강제합니다.
- 복구 중에는 OCR·좌표 터치·뒤로가기·스크롤·중복 해제를 임의 실행하지 않습니다. 실제 보안·권한 오류는 숨기지 않습니다.
-15회 중7회 완료·8회째 대기에서 복구해도 앞선7회를 다시 실행하거나 완료 수를 초기화하지 않습니다. 반복·저장 형식·모든 기존 기능과18차의 작은 접이식 창을 유지합니다.
- 실제 복구 대기 상태가 하단에 표시되고 정지1초 이내 및 후속 입력0을 확인합니다. 기존114개 기기·104개 단위·lint0·엄격UTF8·두APK ID/버전19/기존서명/ABI/CRC·18차153항목 보존·18→19 업데이트를 유지합니다. 새 집중 검사는 개별/전체 제한을 따로 고정합니다.
- 구현자와 다른 검증자가 최종 동결에서 직접 검사합니다. 사용자 블루스택·게임·실제 휴대폰 및24시간 무중단은 시험 기기 결과로 보장하지 않습니다.

## 실제 빌드 경로

새 바로가기·정션·심볼릭 링크와 삭제된17·18차 연결을 만들거나 복원하지 않습니다. 기준 소스는19차/source, 실제 ASCII 빌드 사본은 프로젝트 내부 work/build19/source 일반 폴더입니다. SDK와 JDK·Gradle은 기존 실제 폴더를 사용합니다. 빌드 전 선택 소스를 실제 복사·해시 대조하고 생성 APK를19차에 보관합니다. 한글 경로가 포함된 Java properties는 올바르게 이스케이프합니다. 개인 서명 키는 복사·공개하지 않습니다.

## 최종 회귀에서 추가 확인한 전달 경계

수리3 제품에서 새6개는 통과했지만 첫 최종 묶음은80개 중79PASS/1FAIL이었다. 기존 TargetDispatchBoundaryTest는18차와 원문 동일하고, 마지막 창 확인 뒤 메인 전달을 보류한 상태에서 Settings의 실제 활성 조회가 확인됐으나 permit/live 세대가4/4로 남아 오래된 좌표 제스처 완료가 기록됐다. 원래 앱의 두 번째 버튼 클릭0이며 Settings의 특정 버튼 클릭까지 증명한 것은 아니다. 새 취소 수정이 원인이라고 단정하지 않는다.

별도 일회 진단은 원메서드와 원단언을 그대로 호출하여1PASS였으며 이전 FAIL을 대체하지 않는다. 실제 활성 창 메타가 바뀐 뒤 서비스 revision 증가까지 약57ms 공백을 관측했다. 별도 UiAutomation 이벤트와 실제 서비스 revision의 수신 시각은 서로 다른 채널로 구분했다. 진단 코드는 최종 소스와 검사 APK에서 제외하고 원문은 비공개 운영 자료에 보존한다.

수리6은 실제 수락한 활성/초점 창과 해석된 패키지 식별 변경을 기존 windowRevision에 연결한다. 조회 시작 순번이 더 오래된 결과와 중단·일시정지 세대가 지난 결과는 관측을 덮지 않는다. 수락과 허가 세대 갱신은 같은 임계 구역에서 마치며 메인 스레드의 동기 플랫폼 조회는 추가하지 않는다. 실제로 아직 관측하지 못한 모든 앱 전환까지 원자 차단한다고 보장하지 않는다.

새 관측 모델의 결정적 단위5개를 추가하여109개/20클래스로 검사한다. 원114개 기기와 새6개를 새 최종 동결에서 모두 다시 실행한다. 선택적 성능 명세의18/19 버전 정합도 실제 검사 코드와 대조하며 이번에는 그 비교를 실행하지 않는다. 앞선80개 실패 묶음·새6개 GREEN과 최종 새120개를 소급 혼합하지 않는다.
